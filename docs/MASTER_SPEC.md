# Project WIND — 자체 엔진 기반 2D MMORPG 통합 개발 명세서

- 문서 버전: 1.1
- 상태: 개발 기준 초안
- 대상 플랫폼: Windows PC 우선
- 클라이언트/서버 언어: C++20
- 빌드: CMake
- 렌더링·입력·오디오 기반: SDL3
- 네트워크 기반: ENet
- 운영 데이터베이스: PostgreSQL
- 로컬 개발 데이터베이스: SQLite 선택 가능
- 기본 원칙: 자체 게임 엔진 + 권위 서버 + 단계별 검증

> 이 문서는 고전적인 2D 타일 기반 MMORPG를 독자적으로 개발하기 위한 통합 명세서다. 특정 게임의 소스 코드, 맵, 스프라이트, 음악, 대사, 상표 또는 기타 보호 대상 콘텐츠를 무단 복제하지 않는다. 기존 장르에서 영감을 얻되 모든 게임 콘텐츠와 브랜드는 독자적으로 제작한다.

# 1. 프로젝트 목표와 범위

## 1.1 목표

독자적인 2D 타일 기반 MMORPG를 상용 게임 엔진 없이 개발한다. 게임 클라이언트는 월드 렌더링과 입력을 담당하고, 서버는 게임 상태의 최종 권한을 갖는다. 플레이어는 캐릭터를 생성하고, 필드를 탐험하고, 몬스터를 사냥하고, 아이템을 얻고, 성장하며, 다른 플레이어와 협력한다.

## 1.2 핵심 경험

- 고전적인 2D 픽셀 아트와 타일 기반 월드
- 읽기 쉬운 캐릭터 실루엣과 방향별 애니메이션
- 안정적인 이동 및 다른 플레이어와의 상태 동기화
- 몬스터 사냥, 전투, 경험치, 레벨업
- 아이템 획득, 인벤토리, 장비
- 채팅, 친구, 파티
- 여러 지역을 연결하는 탐험
- 지속 가능한 캐릭터 저장과 서버 운영

## 1.3 범위 단계

### 프로토타입
- 클라이언트와 서버 실행
- 두 개 이상의 클라이언트 접속
- 캐릭터 이동 및 위치 동기화
- 채팅
- 몬스터와 기본 전투
- 경험치·레벨업
- 드롭·인벤토리
- 캐릭터 저장과 재접속

### 확장 버전
- 직업별 기술
- 파티와 친구
- NPC와 퀘스트
- 상점과 장비
- 다수의 맵과 던전
- 운영자 도구

### 운영 버전
- 안전한 계정 인증
- 백업·복구
- 로깅·모니터링
- 부하·보안 테스트
- 패치·배포 자동화
- 신고·제재 기능

## 1.4 초기 제외 범위

모바일, 대규모 공성전, 경매장, 직접 거래, 유료 결제, 현금 재화, 하우징, 펫, 대규모 레이드, 분산 샤딩은 기본 게임 루프와 안정성이 입증된 뒤 검토한다.

## 1.5 제품 원칙

1. 플레이 가능한 작은 버전을 먼저 완성한다.
2. 클라이언트는 권위가 없는 표현 계층으로 취급한다.
3. 게임 규칙은 서버에서 검증한다.
4. 콘텐츠는 코드와 분리한다.
5. 모든 중요한 변경은 테스트와 문서에 반영한다.
6. 과도한 추상화보다 이해하기 쉬운 모듈을 우선한다.
7. 목표 수치는 측정 전까지 보장으로 표현하지 않는다.

# 2. 확정 기술 스택과 개발 원칙

## 2.1 기본 기술 선택

| 영역 | 기본 선택 | 비고 |
|---|---|---|
| 언어 | C++20 | 클라이언트·서버·공통 코드 |
| 빌드 | CMake | 의존성 및 타깃 명시 |
| 플랫폼 라이브러리 | SDL3 | 창, 입력, 렌더러/그래픽 API 연결, 오디오 기반 |
| 네트워크 | ENet | UDP 기반 전송 기능. 게임 프로토콜은 직접 구현 |
| 데이터베이스 | PostgreSQL | 운영 기본값 |
| 로컬 개발 DB | SQLite 선택 | 단위 도구 또는 단일 개발 환경 |
| 콘텐츠 설정 | JSON | 스키마 검증 필수 |
| 테스트 | GoogleTest 또는 Catch2 중 하나 선택 | 초기 단계에서 하나로 고정 |
| 로그 | 검증된 경량 C++ 로그 라이브러리 | 버전 고정 |
| 의존성 관리 | CMake FetchContent 또는 vcpkg 중 하나 선택 | 저장소에서 통일 |
| 버전 관리 | Git | 작은 단위로 커밋 |
| CI | GitHub Actions 또는 동등한 CI | 빌드·테스트 자동화 |

SDL3는 게임 엔진이 아니라 저수준 플랫폼 라이브러리다. 자체 렌더링·맵·애니메이션·게임 오브젝트·UI·게임 루프를 구현한다. ENet은 전송 계층 일부를 제공할 뿐 인증, 게임 규칙, 권한, 데이터 저장을 제공하지 않는다.

## 2.2 의존성 정책

- 외부 라이브러리의 버전과 라이선스를 `DEPENDENCIES.md` 또는 `LICENSES.md`에 기록한다.
- 재현 가능한 빌드를 위해 버전을 고정한다.
- 라이선스가 불명확한 라이브러리를 사용하지 않는다.
- 새로운 라이브러리는 도입 이유, 대안, 라이선스, 유지보수 상태를 기록한다.
- 외부 라이브러리로 게임 엔진 전체를 대체하지 않는다.
- 직접 구현이 가치 없는 저수준 기능은 검증된 라이브러리를 활용한다.

## 2.3 코드 품질 규칙

- C++20 표준을 사용한다.
- 소유권은 RAII와 명확한 수명 규칙으로 관리한다.
- 가능한 경우 값 타입과 명시적 인터페이스를 선호한다.
- `new/delete` 직접 사용을 최소화한다.
- 오류를 무시하지 말고 로그 및 적절한 오류 반환으로 처리한다.
- 전역 가변 상태를 최소화한다.
- 렌더링 코드와 게임 규칙을 분리한다.
- 네트워크 패킷에 C++ 구조체 메모리를 그대로 복사하지 않는다.
- 서버 로직은 클라이언트 렌더러나 SDL에 의존하지 않는다.
- 비밀 키, 비밀번호, 운영 자격 증명을 소스 코드에 넣지 않는다.
- 무관한 파일을 대량으로 재작성하지 않는다.

# 3. 시스템 아키텍처

## 3.1 논리 구성

```text
[Windows Client]
  ├─ Platform / SDL3
  ├─ Custom Engine
  │   ├─ Game Loop
  │   ├─ Renderer
  │   ├─ Tilemap
  │   ├─ Animation
  │   ├─ Camera
  │   ├─ Input
  │   ├─ UI
  │   └─ Resource Manager
  ├─ Game Presentation
  └─ Network Client
          │ ENet + Application Protocol
          ▼
[Authoritative Game Server]
  ├─ Connection / Session
  ├─ Protocol Validation
  ├─ World / Maps
  ├─ Movement / Collision
  ├─ Combat / AI
  ├─ Inventory / Quest / Party
  ├─ Interest Management
  ├─ Persistence Service
  └─ Admin / Metrics
          │
          ▼
[PostgreSQL]
```

## 3.2 클라이언트 책임

- 입력 수집 및 입력 의도 전송
- 서버 상태의 시각화
- 타일맵과 스프라이트 렌더링
- 애니메이션·카메라·UI
- 네트워크 상태 표시
- 사운드 재생
- 사용자 설정 저장

클라이언트가 최종 체력, 피해량, 경험치, 아이템 소유권, 퀘스트 완료를 확정해서는 안 된다.

## 3.3 서버 책임

- 연결·세션 관리
- 요청 검증 및 속도 제한
- 플레이어와 몬스터 상태
- 이동과 충돌 판정
- 전투·피해·사망
- AI와 리스폰
- 아이템 생성·획득·소비
- 경험치와 레벨업
- 지역 전환
- 채팅·파티·퀘스트
- 관심 영역 기반 상태 전송
- 데이터 영속화

## 3.4 서버 실행 모델

초기에는 단일 프로세스·단일 월드 서버로 시작한다. 게임 월드 상태를 변경하는 코드는 한 개의 논리적 월드 실행 흐름에서 직렬화하는 방식을 우선한다. 네트워크 I/O와 데이터베이스 작업은 필요에 따라 분리하되, 월드 상태에 대한 동시 쓰기를 명확하게 통제한다.

초기 서버 틱 목표는 20~30 Hz 중 하나를 프로파일링 전에 설정하고, 첫 구현에서는 20 Hz를 기본값으로 사용한다. 틱 지연을 측정하고 나중에 변경할 수 있도록 설정값으로 둔다. 렌더링 FPS와 서버 틱을 혼동하지 않는다.

## 3.5 모듈 의존성

- `shared`: 플랫폼 독립적 타입, 프로토콜, 직렬화
- `client/engine`: SDL3와 그래픽/입력/오디오
- `client/game`: 게임 상태 표현과 UI
- `client/network`: 서버 통신
- `server`: 게임 규칙과 영속성
- `tools`: 콘텐츠 검증·관리·부하 도구

`shared`는 `client`나 `server`에 의존하지 않는다. 서버는 SDL에 의존하지 않는다. 엔진 모듈은 게임 도메인 규칙에 의존하지 않는다.

# 5. 자체 게임 엔진 상세 설계

## 5.1 게임 루프

작업 순서:
1. OS 이벤트 수집
2. 입력 상태 갱신
3. 네트워크 메시지 수신 및 디코딩
4. 게임 상태 반영
5. 애니메이션·UI 시간 갱신
6. 렌더링
7. 오디오 처리
8. 디버그 계측

렌더링 프레임과 서버 상태 갱신을 분리한다. 긴 프레임이 발생해도 무제한의 catch-up 업데이트가 발생하지 않도록 최대 누적 시간 및 프레임 시간 정책을 정의한다. 클라이언트는 60 FPS를 목표로 하되 하드웨어에 따라 보장한다고 표현하지 않는다.

## 5.2 렌더링 추상화

기본 렌더러는 SDL3 렌더링 API를 사용해도 되지만, 게임의 스프라이트·타일맵·레이어 인터페이스는 엔진 내부에 둔다. 향후 필요할 때 그래픽 백엔드를 교체할 수 있도록 게임 코드가 SDL 렌더링 함수에 직접 의존하지 않게 한다.

필수 기능:
- 텍스처/아틀라스 로딩
- 스프라이트 소스 사각형 지정
- 위치·크기·회전·반전·알파
- 카메라 변환
- 레이어 정렬
- 화면 클리핑
- 타일맵 배치 렌더링
- 디버그 충돌 오버레이
- 렌더링 통계

## 5.3 좌표계

게임 로직은 정수 타일 좌표를 사용한다. 화면 렌더링은 부동소수점 픽셀 좌표를 사용할 수 있다. 다음 변환을 한 곳에서 관리한다.

- 타일 좌표 → 월드 픽셀 좌표
- 월드 좌표 → 화면 좌표
- 화면 좌표 → 월드 좌표
- 월드 좌표 → 타일 좌표

타일 크기는 초기 32×32 논리 픽셀로 설정하되 설정값으로 관리한다. 게임 논리의 타일 크기와 실제 스프라이트 크기를 동일하다고 가정하지 않는다.

## 5.4 픽셀 렌더링

- 픽셀 아트 기본 확대 필터는 최근접 이웃 방식
- 카메라와 스프라이트 위치는 픽셀 정렬 정책을 일관되게 적용
- 원본 해상도와 확대 배율을 설정으로 분리
- 해상도 변경 시 UI와 월드 카메라를 별도 처리
- 고해상도 디스플레이에서 흐림·깜빡임을 확인하는 테스트 제공

## 5.5 타일맵 및 렌더 레이어

# 6. 월드·맵·이동 명세

## 6.1 맵 데이터

맵은 유일한 ID, 너비, 높이, 타일 레이어, 스폰 위치, 출구, 충돌 속성을 가진다. 맵 크기는 초기에는 제한을 두고, 파일 크기·타일 수·레이어 수의 최대치를 검증한다.

예시 구조:

```json
{
  "schema_version": 1,
  "map_id": "starter_meadow",
  "display_name": "초원의 입구",
  "tile_size": 32,
  "width": 64,
  "height": 64,
  "spawn_points": [
    {"id": "default", "x": 10, "y": 10}
  ],
  "layers": [
    {
      "name": "ground",
      "render_order": 0,
      "tiles": []
    }
  ],
  "exits": []
}
```

이 예시는 개념적 스키마다. 타일 압축 방식과 타일셋 참조는 구현 시 별도 확정한다.

## 6.2 이동 규칙

- 초기에는 상하좌우 4방향 이동
- 이동 요청은 서버가 판정
- 타일의 통행 가능 여부는 서버가 로드한 맵 데이터로 확인
- 요청 시퀀스를 사용해 오래되거나 중복된 입력을 판별
- 이동 속도 제한을 서버가 검사
- 맵 경계 밖 좌표는 거부
- 지역 이동은 별도 서버 명령으로 처리
- 클라이언트는 서버 응답을 보간해 표시

## 6.3 이동 상태 데이터

최소 상태:
- entity_id
- map_id
- tile_x, tile_y
- facing
- movement_state
- state_sequence
- server_tick 또는 서버 타임스탬프

## 6.4 지역 전환

1. 클라이언트가 출구 상호작용 요청
2. 서버가 출구와 위치를 검증
3. 서버가 목적지와 스폰 위치를 확인
4. 서버가 지역 상태를 변경
5. 새 지역의 초기 상태를 전송
6. 클라이언트가 이전 지역 엔티티를 정리하고 새 상태를 표시

지역 전환 실패 시 이전 지역 상태를 유지하거나 명시적인 오류를 반환한다.

## 6.5 충돌과 엔티티

초기 충돌은 타일 기반으로 한다. 플레이어끼리 같은 타일을 점유할 수 있는지, 몬스터와 플레이어가 겹칠 수 있는지 등은 게임 규칙으로 명시한다. 시각적 스프라이트 경계와 논리 충돌 영역은 분리한다.

# 8. 전투·몬스터 AI 명세

## 8.1 기본 공격 요청 검증

서버는 다음을 검사한다.
- 공격자 세션 및 캐릭터가 유효한가
- 공격자가 살아 있고 행동 가능한가
- 대상이 존재하고 공격 가능한가
- 같은 맵 또는 전투 영역에 있는가
- 공격 범위 내에 있는가
- 공격 재사용 대기시간이 끝났는가
- 공격자와 대상 사이의 차단 지형 규칙을 만족하는가
- 대상에게 이미 적용된 사망 상태와 상호작용 규칙이 유효한가

## 8.2 피해 계산

모든 피해는 서버에서 계산한다. 초기 예시:

```text
raw_damage = attack_power + skill_power
final_damage = max(minimum_damage, raw_damage - defense)
```

실제 공식은 게임 밸런스 데이터와 테스트로 조정한다. 최소 피해, 피해 상한, 정수 오버플로, 무적 상태, 피해 감소 순서를 명확하게 정의한다. 클라이언트는 결과를 표시할 뿐 피해량을 결정하지 않는다.

## 8.3 전투 이벤트

- attack_started
- damage_applied
- entity_hit
- entity_died
- experience_awarded
- loot_spawned
- loot_acquired

이벤트에는 event_id 또는 적절한 순번, server_tick, 관련 엔티티, 결과를 포함한다. 이벤트는 디버깅과 재현에 충분한 로그를 남기되 비밀 정보를 포함하지 않는다.

## 8.4 사망과 부활

사망 처리:
1. HP를 0으로 고정
2. 행동 불가 상태 설정
3. 진행 중인 전투 동작 취소
4. 드롭/보상 규칙 처리
5. 주변 클라이언트에 사망 이벤트 전달
6. 부활 규칙 적용

초기 버전은 플레이어 아이템·경험치 손실을 기본 비활성화한다. 부활 장소와 대기 시간은 설정으로 관리한다.

## 8.5 몬스터 AI

상태:
- idle
- patrol
- detect
- chase
- attack
- return
- dead

데이터:
- monster_id
- level
- hp
- attack
- defense
- detection_range
- attack_range
- leash_range
- attack_cooldown
- respawn_seconds

AI 업데이트는 설정된 주기로 실행한다. 모든 몬스터를 매 렌더링 프레임마다 갱신하지 않는다. 경로 탐색은 초기에는 단순한 타일 경로 또는 직접 추적으로 시작하고, 필요 시 A*를 추가한다. 경로 탐색은 서버 부하를 측정한 뒤 최적화한다.

## 8.6 드롭 규칙

드롭 테이블은 데이터로 정의한다. 서버는 난수와 드롭 결과를 관리한다. 플레이어가 클라이언트 패킷을 조작해 아이템을 생성할 수 없어야 한다. 다수 플레이어가 동시에 획득 요청을 해도 하나의 아이템 인스턴스가 한 번만 획득되어야 한다.

# 10. 네트워크 프로토콜 상세 명세

## 10.1 기본 원칙

- ENet은 전송 계층이다. 애플리케이션 프로토콜은 직접 정의한다.
- 패킷은 명시적 직렬화/역직렬화를 사용한다.
- C++ 구조체의 메모리 레이아웃을 그대로 전송하지 않는다.
- 각 메시지는 크기 제한과 버전 정책을 가진다.
- 알 수 없는 메시지와 잘못된 길이는 안전하게 거부한다.
- 중요 작업은 request_id 또는 idempotency key로 중복 적용을 방지한다.
- 인증·로그인 비밀은 일반 게임 메시지에 평문으로 반복 전송하지 않는다.
- ENet 자체가 인터넷 전송의 모든 보안 요구를 해결한다고 가정하지 않는다. 공개 서버는 인증, 전송 보호, 비밀 관리, 방화벽 및 운영 정책을 별도로 검토한다.

## 10.2 논리적 헤더

개념적 필드:
- protocol_version: 고정 폭 정수
- message_type: 고정 폭 정수
- request_id: 요청-응답 상관관계 식별자
- payload_length: 페이로드 길이
- payload: 메시지별 필드

실제 바이트 크기와 바이트 순서는 구현 전에 `docs/PROTOCOL.md`에서 확정한다. 최대 패킷 크기를 설정하고, 길이 필드와 실제 수신 길이의 일치 여부를 검사한다.

## 10.4 전송 신뢰성 정책

- 인증·캐릭터 생성·인벤토리 변경·지역 전환 등 중요한 명령은 신뢰성 있는 전달을 사용한다.
- 위치 등 자주 갱신되는 상태는 최신 값이 중요하므로 비신뢰성/비순서 전달을 검토할 수 있다.
- 정확한 채널 번호와 ENet 플래그는 선택한 ENet 버전의 API를 확인한 뒤 구현한다.
- 신뢰성 있는 전달만으로 애플리케이션 수준 중복 처리 문제가 모두 해결된다고 가정하지 않는다.

## 10.5 이동 동기화

클라이언트는 이동 의도와 입력 시퀀스를 전송한다. 서버는 현재 위치, 이동 속도, 통행 가능 여부, 상태를 검증한다. 서버가 수락한 이동 상태를 브로드캐스트한다. 클라이언트는 시각적 보간을 적용한다. 예측을 추가하더라도 서버의 결과가 최종 권위다.

## 10.6 관심 영역(Interest Management)

초기에는 맵 내 타일 기반 반경으로 주변 엔티티를 선택한다. 플레이어에게 필요한 스폰·상태·디스폰 이벤트만 보낸다. 경계에서 엔티티가 중복 생성되거나 영구적으로 사라지지 않는지 테스트한다. 전체 월드 상태를 모든 클라이언트에 보내지 않는다.

## 10.7 연결 종료·재접속

- 정상 로그아웃과 비정상 연결 종료를 구분한다.
- 연결 종료 시 세션·엔티티 상태를 안전하게 정리한다.
- 재접속 시 중복 세션 정책을 적용한다.
- 오래된 요청이나 이전 세션의 패킷을 새 세션에 적용하지 않는다.
- 서버가 종료될 때 저장되지 않은 중요한 변경 사항을 복구할 수 있는 정책을 문서화한다.

## 10.8 프로토콜 호환성

프로토콜 버전을 명시한다. 호환되지 않는 클라이언트는 명확한 오류와 함께 연결을 거부한다. 메시지 필드 변경 시 이전 버전과의 호환 여부를 검토하고 `docs/DECISIONS/`에 기록한다.

# 11. 계정·인증·세션

## 11.1 계정 기능

- 계정 생성
- 로그인
- 로그아웃
- 세션 만료
- 계정별 캐릭터 목록
- 중복 로그인 정책
- 계정 상태 확인

## 11.2 비밀번호

비밀번호는 평문이나 단순 해시로 저장하지 않는다. Argon2id 등 적절한 비밀번호 해시 알고리즘과 검증된 구현체를 사용한다. 비밀번호·세션 비밀·토큰을 로그에 기록하지 않는다. 공개 네트워크에 서비스를 제공하기 전 인증 요청 보호와 전송 보안을 별도 검토한다.

## 11.3 세션

세션은 계정과 캐릭터의 권한을 서버 측에서 연결한다. 세션 식별자는 충분한 무작위성을 가져야 하며 클라이언트 입력만으로 권한이 결정되어서는 안 된다. 세션 만료, 재접속, 중복 로그인, 강제 로그아웃 정책을 문서화한다.

## 11.4 개발 전용 인증

테스트 계정이나 로컬 인증 우회는 개발 환경에만 허용한다. 운영 모드에서 우회 인증이 활성화되면 서버 시작을 실패시키는 안전장치를 둔다. 비밀 키는 환경 변수 또는 비밀 관리 도구로 주입한다.

## 12.2 제약과 인덱스

- 외래 키와 고유 제약 조건을 적용한다.
- 레벨·경험치·수량의 범위를 검증한다.
- 자주 조회하는 account_id, character_id, map_id 등에 필요한 인덱스를 둔다.
- 실제 쿼리 패턴에 맞춰 인덱스를 검토한다.
- DB 제약과 서버 검증을 함께 사용한다.

## 12.3 마이그레이션

- 모든 스키마 변경은 순서가 있는 마이그레이션 파일로 제공한다.
- 적용된 마이그레이션을 기록한다.
- 개발 DB 초기화와 운영 데이터 마이그레이션을 구분한다.
- 파괴적 변경은 백업과 롤백 계획 없이 적용하지 않는다.
- 콘텐츠 데이터 버전과 DB 스키마 버전을 혼동하지 않는다.

## 12.4 영속화와 트랜잭션

실시간 이동을 매 프레임 DB에 기록하지 않는다. 중요한 인벤토리·장비·보상 변경은 트랜잭션으로 처리한다. 메모리 상태와 DB 저장 사이에 오류가 발생할 때 복구 가능한 정책을 정한다. 캐릭터 위치 저장 주기와 비정상 종료 시 허용 가능한 롤백 범위를 명시한다.

## 12.5 DB 연결 관리

- 연결 풀 또는 명확한 연결 수명 관리
- 쿼리 타임아웃
- 파라미터 바인딩
- DB 오류 로그
- 재시도 가능한 오류와 불가능한 오류 구분
- DB 장애 시 무한 대기 금지
- 비밀 정보의 설정 파일 커밋 금지

# 16. 콘텐츠 데이터 형식 및 검증

## 16.1 콘텐츠 원칙

몬스터·아이템·스킬·퀘스트·NPC·맵은 코드에서 가능한 한 분리한다. 데이터 형식에는 `schema_version`을 포함하고, 데이터 로드 전에 검증한다.

## 16.2 몬스터 예시

```json
{
  "schema_version": 1,
  "id": "monster_slime_001",
  "name": "초원 슬라임",
  "level": 1,
  "max_hp": 30,
  "attack_power": 3,
  "defense": 0,
  "experience_reward": 5,
  "aggro_range": 4,
  "respawn_seconds": 10
}
```

## 16.3 아이템 예시

```json
{
  "schema_version": 1,
  "id": "item_small_potion",
  "name": "작은 회복 물약",
  "type": "consumable",
  "max_stack": 20,
  "usable": true,
  "effects": [
    {"type": "heal_hp", "value": 25}
  ]
}
```

## 16.4 검증 도구

다음 오류를 검출한다.
- 중복 ID
- 누락된 필수 필드
- 잘못된 참조
- 잘못된 숫자 범위
- 존재하지 않는 이미지·오디오
- 존재하지 않는 맵 좌표
- 잘못된 퀘스트 연결
- 잘못된 아이템/스킬 참조
- 비정상적으로 큰 파일·배열
- 알 수 없는 스키마 버전

검증 실패 시 콘텐츠를 로드하지 않고 파일명과 필드 경로를 포함한 오류를 출력한다.

# 17. 보안·악용 방지

## 17.1 신뢰 경계

모든 클라이언트 데이터는 신뢰할 수 없는 입력이다. 서버는 이동·전투·아이템·경험치·재화·퀘스트·권한을 직접 검증한다.

## 17.2 입력 제한

- 최대 패킷 크기
- 최대 문자열 길이
- 메시지별 허용 상태
- 요청 빈도 제한
- 잘못된 패킷 카운터
- 연결별 리소스 제한
- 알 수 없는 메시지 거부
- 비정상 입력 시 안전한 연결 종료 정책

## 17.3 경제·아이템 보안

- 획득과 보상 지급의 중복 방지
- 아이템 소유권의 단일 원본 유지
- 수량 범위 검사
- 재화 변경의 원자성
- 운영자 아이템 지급 로그
- DB 장애·재시도 시 복제 방지

## 17.4 운영자 권한

운영자 명령은 권한 수준별로 제한한다. 위험한 명령은 사유·실행자·대상·시간을 감사 로그에 남긴다. 운영자 자격 증명을 소스에 넣지 않는다.

## 17.5 공개 서비스 전 필수 검토

- 인증과 비밀번호 해시
- 전송 보호 및 키 관리
- 방화벽과 포트 노출

# 22. Claude 개발 운영 규칙

## 22.1 작업 시작 전

Claude는 먼저:
1. 현재 저장소 구조를 조사한다.
2. README와 관련 설계 문서를 읽는다.
3. 현재 빌드 및 테스트 상태를 확인한다.
4. 관련 코드와 인터페이스를 살핀다.
5. 변경 파일과 완료 기준을 제시한다.

기존 코드가 있는 프로젝트에서는 무조건 새로 만들거나 덮어쓰지 않는다.

## 22.2 작은 작업 단위

한 작업에서 하나의 기능 경계만 구현한다. 예: 패킷 타입 정의 → 직렬화 테스트 → 서버 검증 → 클라이언트 연동 순으로 진행한다.

## 22.3 모호한 요구

- 기존 명세와 충돌하는지 먼저 확인한다.
- 위험이 낮으면 가장 단순하고 확장 가능한 기본안을 선택한다.
- 보안, DB 마이그레이션, 프로토콜 호환성, 데이터 삭제 등 위험이 큰 결정은 변경 전 계획과 영향을 명시한다.
- 중요한 결정을 `docs/DECISIONS/`에 기록한다.

## 22.4 테스트와 보고

작업 완료 보고 형식:

```text
작업명:
변경된 파일:
구현 내용:
인터페이스/스키마 변경:
실행한 빌드 명령:
실행한 테스트:
테스트 결과:
미해결 문제:
다음 작업:
```

실제로 실행하지 않은 명령이나 테스트를 실행했다고 말하지 않는다. 빌드 환경이 없어 확인하지 못했다면 명확하게 표시한다.

## 22.5 금지 사항

- 전체 프로젝트를 한 번에 생성하려고 하지 않는다.
- 빌드 오류를 숨기거나 테스트를 삭제해 통과시키지 않는다.
- 무관한 코드를 대량으로 포맷하거나 재작성하지 않는다.
- 명세에 없는 복잡한 기능을 임의로 추가하지 않는다.
- 비밀 값이나 운영 자격 증명을 코드에 넣지 않는다.
- 기존 인터페이스를 조용히 바꾸지 않는다.
- TODO만 작성하고 구현했다고 보고하지 않는다.

# 23. CLAUDE.md 초안

아래 내용을 저장소 루트의 `CLAUDE.md`로 복사해 사용할 수 있다.

```markdown
# Project WIND — Claude Instructions

## Project
Build an original Windows-first 2D tile-based MMORPG using C++20, CMake, SDL3, ENet, and PostgreSQL. Do not use Unity, Unreal, Godot, or another full game engine. SDL3 and ENet are allowed low-level libraries; implement the game engine systems in this repository.

## Source of truth
- `docs/REQUIREMENTS.md`: product requirements
- `docs/ARCHITECTURE.md`: module boundaries
- `docs/ENGINE.md`: custom engine design
- `docs/PROTOCOL.md`: network wire format
- `docs/DATABASE.md`: schema and migrations
- `docs/GAMEPLAY.md`: gameplay rules
- `docs/SECURITY.md`: trust boundaries and validation
- `docs/TESTING.md`: test policy
- `docs/DECISIONS/`: accepted architectural decisions

If a document does not exist yet, create or update it as part of the relevant task. Do not silently invent conflicting rules.

## Mandatory workflow
1. Inspect the repository and read relevant docs before editing.
2. State the small task, files likely to change, and acceptance criteria.
3. Implement only that task.
4. Build the affected targets.
5. Run relevant tests.
6. Inspect the diff for unrelated changes and security issues.
7. Update docs when interfaces, protocol, schema, or behavior changes.
8. Report commands actually run and their real results.

## Architecture rules
- Server is authoritative for movement, combat, HP, XP, inventory, currency, quest rewards, and permissions.
- Client is presentation/input; never trust client-provided outcomes.
- `shared` must not depend on `client` or `server`.
- Server code must not depend on SDL or rendering.
- Do not send raw C++ struct memory over the network. Use explicit serialization.
- All untrusted network input must be length-checked and validated.
- Important inventory/reward operations must be idempotent or transactionally protected.
- Use migrations for database schema changes.
- Keep content data separate from gameplay code and validate it before loading.

## C++ rules
- C++20.
- Prefer RAII, explicit ownership, small functions, and clear interfaces.
- Avoid global mutable state and unexplained magic numbers.
- Do not swallow errors.
- Do not add dependencies without recording version, license, and rationale.
- Do not commit secrets or real credentials.
- Do not disable or delete tests just to get a green build.

## Scope control
Do not attempt to implement the whole MMORPG in one task. Follow the phases in the master specification. Prefer a small working vertical slice over broad placeholder code.

## Completion report
Include:
- Task
- Files changed
- Behavior implemented
- Interface/schema changes
- Build command and result
- Tests run and result
- Known limitations
- Next task

Never claim a build or test passed unless it was actually run and passed.
```

```text
타일 좌표와 화면 좌표 변환에 대한 단위 테스트를 추가하라. 클라이언트가 실행되고 샘플 맵과 테스트 캐릭터를 표시하는지 확인하라. 빌드와 테스트 결과를 보고하라.
```

## 프롬프트 3 — 프로토콜과 네트워크 연결

```text
단계 2의 네트워크 기반만 구현하라. 먼저 docs/PROTOCOL.md에서 메시지 헤더, 바이트 순서, 최대 패킷 크기, 메시지 ID, 요청 ID, 버전 호환 정책을 명확히 정의하라.

그다음 ENet 기반 연결, 명시적 직렬화/역직렬화, 패킷 길이 검사, 알 수 없는 메시지 거부, 연결 종료 처리를 구현하라. C++ 구조체 메모리를 그대로 전송하지 마라.

잘못된 패킷, 짧은 패킷, 지나치게 큰 길이, 알 수 없는 메시지 ID에 대한 테스트를 추가하라. 이동이나 전투 기능은 아직 구현하지 마라. 빌드와 테스트 결과를 보고하라.
```

## 프롬프트 4 — 서버 권위 이동과 멀티플레이어

```text
서버 권위 타일 이동을 구현하라. 클라이언트는 이동 의도와 입력 시퀀스를 보내고, 서버는 현재 위치·맵 경계·통행 가능 타일·이동 속도·캐릭터 상태를 검증한다.

서버가 승인한 위치 상태만 클라이언트에 반영한다. 두 개 이상의 클라이언트가 같은 맵에서 서로를 볼 수 있어야 한다. 관심 영역 동기화의 초기 버전은 단순한 맵 내 반경 기반으로 구현하라.

서버가 거부한 이동, 오래된 입력, 연결 종료, 주변 엔티티 생성/제거를 테스트하라. 프로토콜과 아키텍처 문서를 업데이트하고 실제 결과를 보고하라.
```

## 프롬프트 5 — 몬스터와 전투

```text
몬스터 생성, 간단한 상태 머신 AI, 기본 공격, 피해 계산, 사망, 경험치, 레벨업을 구현하라.

모든 결과는 서버에서 계산한다. 공격자의 상태, 대상, 거리, 맵, 공격 쿨다운을 검증한다. 피해 계산은 순수 함수로 분리하고 경계값 테스트를 작성하라. 몬스터 데이터는 JSON 콘텐츠로 정의하고 스키마 검증을 추가하라.

단계별로 빌드와 테스트를 실행하고, 테스트하지 않은 기능은 완료로 표시하지 마라.
```

## 프롬프트 6 — 아이템과 영속성

```text
아이템 정의와 아이템 인스턴스를 구분하고, 드롭·획득·인벤토리·아이템 사용을 구현하라. 아이템 획득은 동시 요청과 중복 요청에 안전해야 한다.

PostgreSQL 스키마와 순서가 있는 마이그레이션을 추가하라. 계정, 캐릭터, 인벤토리, 장비의 저장과 재접속 복구를 구현하라. 비밀번호는 검증된 비밀번호 해시 알고리즘으로 처리하고 평문으로 저장하지 마라.

DB 장애, 중복 획득, 인벤토리 공간 부족, 재접속 복구를 테스트하라. 개발용 인증 우회가 운영 모드에서 켜지지 않도록 보호하라.
```

## 프롬프트 7 — 협동 시스템

```text
지역 채팅, 귓속말, 파티 생성·초대·수락·탈퇴, 기본 NPC 상호작용과 퀘스트를 구현하라.

모든 권한과 보상은 서버에서 검증한다. 채팅 길이와 빈도를 제한하고, 퀘스트 보상 중복 수령을 방지하라. 클라이언트 두 개 이상으로 통합 테스트를 작성하라. 관련 문서를 갱신하고 결과를 보고하라.
```

# 최종 지시

이 문서를 Project WIND의 통합 개발 기준으로 사용한다.

가장 먼저 저장소와 개발 환경을 조사하고, 단계 0만 구현한다. 그 단계의 완료 조건을 충족하기 전에는 이후 기능을 대량으로 구현하지 않는다.

불명확한 세부 사항은 현재 문서와 충돌하지 않는 가장 단순한 설계를 제안한다. 보안·프로토콜·DB 스키마처럼 변경 비용이 큰 사항은 구현 전에 설계와 테스트 계획을 제시한다.

최종 목표는 파일 수가 많은 코드가 아니라, 실제로 빌드·실행·테스트할 수 있고 다른 개발자가 이해하고 확장할 수 있는 자체 엔진 기반 MMORPG다.
